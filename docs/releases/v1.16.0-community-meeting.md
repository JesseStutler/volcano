# Volcano v1.16.0 Community Meeting Walkthrough

Speaker notes for a roughly five-minute walkthrough.

## Opening

Hi everyone. I'd like to give a quick walkthrough of Volcano v1.16.0. I'll focus on the main features, then cover a few other improvements and fixes.

The release gives platforms more flexibility in how they manage tenants, expands the HyperNode ecosystem, and improves scheduling performance.

## Scheduler performance

First, performance. One major addition is the Unschedulable Job Cache.

When many Jobs are waiting for the same resource or placement constraint, repeatedly checking them can consume scheduling time without helping them make progress. The cache records why a Job could not be scheduled and uses relevant events to trigger another evaluation. This reduces repeated checks and helps runnable Jobs make progress under a large pending backlog.

The cache is opt-in. Jobs outside its supported coverage follow normal scheduling, and a watchdog provides periodic retries.

There are also improvements beyond the cache. Scoring plugins can share a node traversal, and node updates and queue lookups avoid unnecessary copying and traversal. We will continue improving performance based on benchmarks and production feedback.

## NamespaceQueue

Next is NamespaceQueue. This supports platforms where namespaces are the tenant management boundary.

Administrators authorize access to a cluster resource pool. Tenants can then create queue hierarchies and manage quotas inside their own namespaces. This gives them Volcano's hierarchical queue capabilities within their existing ownership boundary.

NamespaceQueue is opt-in and uses hierarchical capacity scheduling. One detail to keep in mind is that the new unschedulable Job cache does not currently cache hierarchical capacity rejections.

## Fairshare

Fairshare addresses another tenant model: several namespaces sharing the same queue.

It uses a Slurm-inspired approach that tracks historical resource consumption and gradually decays older usage. Namespaces that have consumed less receive earlier scheduling consideration. This helps when one team continuously submits GPU jobs and another team joins later.

It complements fairness based on current allocation. It changes pending-job ordering and can optionally control admission, without preempting running Jobs.

## PodGroup topology anti-affinity

For inference services, keeping the Pods of one instance close together is only part of the placement requirement. We may also want different instances in different topology domains.

PodGroup topology anti-affinity adds required and preferred separation rules across HyperNode domains. Combined with network topology constraints, it lets each instance stay together while spreading different instances across supernodes.

These rules apply during allocation. BestEffort Pods placed through backfill are outside that guarantee.

## HyperNode and ecosystem progress

The HyperNode controller can now run on its own. Platforms using other schedulers can reuse topology discovery and supernode management, then consume the topology through the HyperNode API. They do not need to run the other Volcano components.

Separately, Grove and KubeRay have integrated Volcano's multi-level gang scheduling for workload roles and worker replicas. Those integrations build on capabilities available since v1.14. SubGroup-level topology integration remains future work in both projects.

## Other improvements and selected fixes

A few other improvements are worth mentioning. Load estimation helps bulk Pod scheduling account for newly assigned workloads before monitoring catches up. Pod-level NUMA allocation reporting improves the accuracy of CPU availability decisions. The release also includes Kubernetes 1.36 support, DRA scoring, and resource limits per nodegroup.

On fixes, I'll highlight queue accounting and scheduling recovery. Admission failures no longer leave phantom quota reservations, and ancestor quota checks account for scheduling-gate reservations. Completed PodGroups retain their state after Pod cleanup, and Pods can recover when newly created PVCs are not yet visible to the scheduler.

The release also includes the DRA capacity-accounting security fix first shipped in v1.15.2.

## Closing

Thanks to everyone who contributed. I'd especially welcome feedback on the tenant models, HyperNode integration, and performance under real workloads. The release note has the configuration examples and upgrade details, and I'm happy to discuss any of these features.
