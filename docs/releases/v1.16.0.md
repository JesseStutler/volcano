## Summary

Volcano v1.16.0 introduces NamespaceQueue and the fairshare plugin to support different tenancy models. Tenants can manage queue hierarchies and quotas within their own namespaces, using administrator-authorized resource pools. For tenants isolated by namespace and sharing a queue, fairshare adds Slurm-inspired historical usage decay to improve long-term fairness.

This release also broadens the HyperNode ecosystem. Other schedulers can reuse topology discovery and supernode management through the independently deployable HyperNode controller and its API. PodGroup topology anti-affinity separates workload instances across topology domains. Scheduler performance improvements include the Unschedulable Job Cache, shared node traversal for scoring plugins, and lower overhead in cache updates and queue lookups. Additional changes include load estimation for bulk Pod dispatch, Kubernetes 1.36 support, DRA scoring, queue-level quotas per nodegroup, accelerator enhancements, and stability fixes.

## What's New

### Key Features Overview

- **Scheduler Performance and Scalability**: Reduces backlog retries with an unschedulable Job cache and improves node scoring, cache updates, and queue lookups.
- **Namespace-scoped Queues**: Lets tenants configure queue hierarchies and quotas within their namespaces, using administrator-authorized resource pools.
- **Per-Namespace Fair Share Scheduling**: Applies Slurm-inspired usage decay to improve long-term fairness among tenants isolated by namespace and sharing a queue.
- **PodGroup Topology Anti-Affinity**: Separates workload instances across HyperNode domains with required or preferred placement rules.
- **Broader HyperNode Integration with Other Schedulers**: Makes topology discovery and supernode management available through a standalone controller and the HyperNode API.

### Key Feature Details

### Scheduler Performance and Scalability

**Background and Motivation**:

v1.16.0 introduces the Unschedulable Job Cache to improve scheduling under large pending backlogs, alongside improvements to node scoring, cache updates, and queue lookups.

**Unschedulable Job Cache**

Pending Jobs may remain blocked by queue quotas, insufficient resources, or placement constraints across many scheduling sessions. Repeating the same checks in every session consumes time that could be used to schedule other Jobs.

The `UnschedulableJobCache` records why a Job could not be scheduled and uses plugin-provided event hints to decide when it should be evaluated again. Later sessions skip the checks covered by the cached result until a relevant change occurs. This reduces redundant work and improves scheduling performance in clusters with persistent unschedulable backlogs.

**Key Capabilities**:

- **Selective skipping**: Uses recorded rejection causes to skip enqueue checks, whole-Job evaluation, or checks for specific tasks while respecting gang requirements.
- **Event-driven wakeups**: Retries Jobs when relevant conditions change. For example, a Node label update can wake a Job blocked by node affinity, resource release can wake a resource-blocked Job, and a Queue update can wake a Job blocked by quota. Storage and DRA events are also supported through plugin hints.
- **Safe fallback**: Caches a Job only when every rejecting plugin provides a safe event hint. Other Jobs continue through normal per-session evaluation.
- **Gang and fairness preservation**: Keeps cached Jobs visible to pending demand, queue accounting, and gang requirements. All normal scheduling checks run again before placement after a wakeup.
- **Bounded retries**: A configurable watchdog retries cached Jobs after a maximum skip duration, defaulting to five minutes. The cache is in memory and is cleared on scheduler restart.

**Configuration**:

The feature is disabled by default. Enable it with the scheduler feature gate:

```bash
helm upgrade --install volcano volcano-sh/volcano \
  --namespace volcano-system --create-namespace --version 1.16.0 \
  --set custom.scheduler_feature_gates="UnschedulableJobCache=true"
```

Initial coverage includes the upstream predicates integrated by Volcano, native Resource Fit, proportion, and non-hierarchical capacity. Hierarchical capacity rejections and rejections from plugins without hint providers continue to be evaluated each session.

Optional debug metrics report cache skips, event wakeups, and watchdog expirations. They are disabled by default because they carry Job identity labels. Enable them when needed with `custom.scheduler_unschedulable_job_cache_debug_metrics=true` and scheduler metrics enabled.

### Namespace-scoped Queues

**Background and Motivation**:

Platforms use different tenancy models. Some assign resource pools to tenants through cluster-scoped Queues. Others use namespaces as the management boundary for teams or projects and want tenants to configure queue quotas and hierarchies within that boundary. NamespaceQueue supports this namespace-based model, aligning queue management with tenant ownership.

NamespaceQueue extends hierarchical queue management to namespaces while preserving administrator control over resource-pool authorization. Tenants can create parent/child queues and configure resource attributes within their namespaces. The resource integrates with the scheduler's common queue model, allowing cluster Queues and NamespaceQueues to participate in the same resource hierarchy.

**Key Capabilities**:

- A namespaced `NamespaceQueue` CRD with capability, deserved, guarantee, priority, reclaimability, and dequeue strategy settings.
- Namespace-local parent/child hierarchies, with `cluster/<name>` references for cluster Queue parents.
- Administrator authorization through cluster Queue `spec.allowedNamespaces`. Omitted or empty lists deny NamespaceQueue attachment, and `["*"]` allows all namespaces.
- Explicit workload references through `spec.queue: namespace/<name>`, resolved within the workload's namespace. Bare queue names continue to reference cluster Queues.
- Controller-maintained authorization and readiness conditions, with final scheduler readiness checks before admission.

**Configuration**:

The feature is disabled by default. The Helm switch enables `NamespaceQueue=true` for the controller manager, scheduler, and admission webhook and selects the hierarchical capacity configuration when using the chart's default scheduler configuration. Custom scheduler configurations must enable `capacity` with `enableHierarchy: true`. Initial NamespaceQueue support is limited to the capacity plugin. Do not enable proportion alongside it. NamespaceQueue hierarchies allow five levels below a cluster Queue by default. Set `--max-namespacequeue-depth` on both the controller manager and admission webhook to change that limit.

```bash
helm upgrade --install volcano volcano-sh/volcano \
  --namespace volcano-system --create-namespace --version 1.16.0 \
  --set custom.namespace_queue_enable=true
```

Create the namespace and an authorized parent Queue first, grant tenants namespace-local RBAC permissions for `namespacequeues`, then create the NamespaceQueue. Wait for `Ready=True` and confirm `Authorized=True` before submitting workloads:

```yaml
apiVersion: v1
kind: Namespace
metadata:
  name: team-a
---
apiVersion: scheduling.volcano.sh/v1beta1
kind: Queue
metadata:
  name: research
spec:
  capability:
    cpu: "100"
    memory: "200Gi"
  deserved:
    cpu: "100"
    memory: "200Gi"
  allowedNamespaces:
  - team-a
---
apiVersion: scheduling.volcano.sh/v1beta1
kind: NamespaceQueue
metadata:
  name: training
  namespace: team-a
spec:
  parent: cluster/research
  capability:
    cpu: "40"
    memory: "80Gi"
  deserved:
    cpu: "40"
    memory: "80Gi"
  reclaimable: true
```

Reference it in a Job or PodGroup in `team-a`:

```yaml
spec:
  queue: namespace/training
```

### Per-Namespace Fair Share Scheduling

**Background and Motivation**:

Volcano organizes resource sharing and quota governance around cluster-scoped Queues, which fits deployments that assign a dedicated queue to each tenant. Other platforms isolate teams or projects by namespace, with multiple tenants submitting into one Queue. These deployments need fairness within the shared queue as well as fairness across queues.

Current-allocation snapshots do not capture resource consumption over time. A namespace submitting a continuous stream of GPU jobs can repeatedly regain scheduling priority as its jobs finish, leaving later arrivals with little opportunity to run.

Inspired by Slurm fair-share scheduling, the new `fairshare` plugin tracks cumulative resource-seconds per namespace within a queue and applies exponential half-life decay. Lower historical consumption receives earlier consideration, while older usage gradually loses influence. This complements DRF's current-resource fairness and requires no administrator-assigned namespace weights.

**Key Capabilities**:

- Historical usage ordering within a queue, with a default four-hour half-life.
- Configurable target queues and tracked resource keys, including per-queue resource overrides.
- Optional enqueue gating and ConfigMap persistence across scheduler restarts.
- Namespace fair-share and decayed-usage metrics.

**Configuration**:

Add `fairshare` to the scheduler configuration before `drf`. Keep `priority` first if PriorityClass should take precedence. Plugin list order determines which comparison wins. This example shows a complete basic configuration using the capacity plugin:

```yaml
actions: "enqueue, allocate, backfill"
tiers:
- plugins:
  - name: priority
  - name: gang
  - name: conformance
  - name: fairshare
    arguments:
      fairshare.targetQueues: "gpu-queue"
      fairshare.resourceKey: "nvidia.com/gpu"
      fairshare.halfLifeMinutes: "240"
      fairshare.enableEnqueueGate: "false"
      fairshare.persistState: "false"
- plugins:
  - name: drf
  - name: capacity
  - name: predicates
  - name: nodeorder
```

Fairshare influences pending-job ordering and optional enqueue admission. It does not preempt or reclaim already-running jobs. Persistence is disabled by default. Enabling it uses the configurable `fairshare.stateNamespace`, `fairshare.stateConfigMap`, and `fairshare.flushIntervalSeconds` settings.

### PodGroup Topology Anti-Affinity

**Background and Motivation**:

Network topology scheduling can keep a workload together within one HyperNode domain, but this does not by itself separate different workload instances. Multiple inference replicas may all land in one supernode, exposing the service to a shared failure domain.

PodGroup anti-affinity expresses isolation at the workload-group level. It selects peer PodGroups by labels and namespace selectors and applies the separation rule at a named or numbered HyperNode tier. The scheduler intersects this policy with existing network topology constraints before evaluating placement.

**Key Capabilities**:

- Required rules for mandatory separation and preferred rules for best-effort separation.
- Selection of peer PodGroups in the current namespace, all namespaces, or namespaces matching labels.
- Composition with `networkTopology` so each group can stay together while different groups use separate domains.
- Explicit unconstrained, constrained, and rejected HyperNode gradient results for composing topology plugins.

**Configuration**:

Add these entries to the existing scheduler plugin list and retain the other configured actions/plugins:

```yaml
- name: group-topology-affinity
  arguments:
    weight: 10
- name: network-topology-aware
  arguments:
    weight: 10
```

The HyperNode tree must contain the specified tier. Apply the following policy to each PodGroup requiring mutual isolation, changing its name for each instance:

```yaml
apiVersion: scheduling.volcano.sh/v1beta1
kind: PodGroup
metadata:
  name: inference-a
  namespace: default
  labels:
    app: model-a
spec:
  minMember: 2
  queue: default
  networkTopology:
    mode: hard
    highestTierName: supernode
  topologyAffinity:
    podGroupAntiAffinity:
      required:
      - podGroupSelector:
          matchLabels:
            app: model-a
        topologyTierName: supernode
```

Rules select PodGroup labels, not Pod labels. Each term must specify exactly one of `topologyTierName` and `topologyTier`. Preferred terms additionally require a weight from 1 to 100. Required terms omit weight. Member Pods must use `schedulerName: volcano` and their PodGroup's `scheduling.k8s.io/group-name` annotation.

The plugin must be enabled explicitly. Enforcement applies to `allocate`. BestEffort Pods placed through backfill do not receive this isolation guarantee. SubGroup affinity/anti-affinity, cross-PodGroup affinity, relocation of running Pods, and eviction solely to clear an anti-affinity conflict are outside the implemented scope.

### Broader HyperNode Integration with Other Schedulers

**Background and Motivation**:

Platforms using other schedulers also need to discover cluster topology and manage supernodes and their hierarchy. v1.16.0 makes the HyperNode controller independently deployable, opening its topology discovery and management capabilities to more scheduling systems.

Platforms can deploy just the HyperNode controller, reuse discovery methods including UFM and node labels, and manage supernodes through HyperNode resources. Other schedulers can consume that topology through the HyperNode API to implement topology-aware placement. Standalone and integrated deployments share the discovery and reconciliation implementation, so improvements can serve both modes. HyperNode remains part of Volcano's source and release lifecycle.

**Key Capabilities**:

- A dedicated `vc-hypernode-controller-manager` binary, image, Deployment, RBAC, and Helm configuration.
- `controller-manager`, `standalone`, and `disabled` deployment modes, with integrated mode retained as the default.
- Shared discovery and reconciliation behavior across integrated and standalone modes.
- Independent resource, replica, placement, logging, health, and metrics settings.

**Configuration**:

For a topology-only installation:

```bash
helm upgrade --install volcano volcano-sh/volcano \
  --namespace volcano-system --create-namespace --version 1.16.0 \
  --set custom.hypernode_controller_mode=standalone \
  --set custom.controller_enable=false \
  --set custom.scheduler_enable=false \
  --set custom.admission_enable=false
```

Discovery uses the existing `custom.controller_config_override` configuration. When migrating an existing integrated installation, first set `custom.hypernode_controller_mode=disabled` and wait for the controller-manager rollout before enabling `standalone`, so only one process reconciles HyperNodes. To retain other Volcano components, change only the HyperNode mode.

## Other Notable Changes

### Features and Enhancements

#### Load-Aware Scheduling for Bulk Pod Dispatch

**Background and Motivation**:

Monitoring data arrives after workload placement. During a large scheduling burst, a node can still look lightly loaded even after receiving many Pods, causing subsequent placements to concentrate on that node before Prometheus or another metrics backend catches up.

The `usage` plugin now maintains a session-level shadow load cache for assigned Pods whose usage is not yet visible in metrics. Scoring uses measured load plus estimated CPU and memory consumption. Each estimate is recorded as a per-Pod snapshot, so allocation rollback removes the same estimate rather than recomputing it against a changed node state.

**Key Capabilities**:

- Session warm-up for assigned Pending Pods and recently started Running Pods within the metrics delay window.
- Incremental estimated-load updates on allocation and deallocation.
- Configurable request, burst, and load-risk estimation, plus fixed BestEffort estimates.
- Safe fallback when monitoring data is missing or stale.

**Configuration**:

Add or update this plugin entry in the existing scheduler configuration. Keep the metrics source configured. The `metrics.interval` setting defines the monitoring delay window and defaults to 30 seconds.

```yaml
- name: usage
  enablePredicate: false
  arguments:
    usage.weight: 5
    cpu.weight: 1
    memory.weight: 1
    estimator:
      request_ratio: 0.7
      burst_ratio: 0
      risk_threshold: 0.6
      risk_factor: 1.2
      be_cpu: 250m
      be_mem: 200Mi
```

For Guaranteed and Burstable Pods, the estimate is `(request * request_ratio + (limit - request) * burst_ratio) * applied_risk_factor`, clamped to the effective limit. Missing or undersized limits fall back to the request. Setting `enablePredicate: false` retains scoring without rejecting new Pods solely because a usage threshold has been reached.

### Ecosystem Updates

Grove and KubeRay have integrated Volcano's multi-level gang scheduling to support finer-grained scheduling requirements for workload roles and replicas.

- **Grove**: Its merged Volcano scheduler backend maps workload roles to SubGroups within a PodGroup, supporting role-level gang constraints. ([PR #516](https://github.com/ai-dynamo/grove/pull/516))
- **KubeRay**: Merged support translates Ray worker group replica settings into `SubGroupPolicy`, allowing gang constraints to require complete replicas, including multi-host replicas. ([PR #5249](https://github.com/ray-project/kuberay/pull/5249))

Both integrations currently cover subgroup-level gang constraints. SubGroup-level network topology-aware scheduling is not yet integrated in either project.

Note: Multi-level gang scheduling has been supported since Volcano v1.14 and is not exclusive to v1.16.

### API Changes

- **NamespaceQueue and parent authorization**: Adds `scheduling.volcano.sh/v1beta1` NamespaceQueue, generated clients/informers, status conditions, cluster Queue `spec.allowedNamespaces`, and workload queue references using `namespace/<name>`. Enable with Helm `custom.namespace_queue_enable`. Custom deployments must enable `NamespaceQueue` in all three participating components and use hierarchical capacity. Cross-namespace parent references are unsupported. ([#5590](https://github.com/volcano-sh/volcano/pull/5590), @gitGurugu)
- **PodGroup topology policy**: Adds `spec.topologyAffinity.podGroupAntiAffinity` with required/preferred terms, PodGroup and namespace selectors, and HyperNode tier selection. The key feature section shows the supported API. ([#5349](https://github.com/volcano-sh/volcano/pull/5349), @wangyang0616)
- **NUMA allocation reporting**: Adds `Numatopology.spec.podAllocations` with Pod UID, name, namespace, and per-container resource allocations. CPU allocations use cpuset strings. The scheduler consumes these reports to distinguish released resources from placements still awaiting kubelet allocation. Use a resource-exporter version that reports the new field. ([#5467](https://github.com/volcano-sh/volcano/pull/5467), [#5504](https://github.com/volcano-sh/volcano/pull/5504), @Tau721, [Issue #5466](https://github.com/volcano-sh/volcano/issues/5466), [Issue #5500](https://github.com/volcano-sh/volcano/issues/5500))
- **Topology plugin interface change**: Changes `HyperNodeGradientForJobFn` and `HyperNodeGradientForSubJobFn` to return `HyperNodeGradientResult`. `Unconstrained: true` explicitly permits the subtree. Otherwise empty gradients reject it. Adds optional `HyperNodeCandidateFn` nomination validation. Custom topology plugins must adapt and rebuild. ([#5349](https://github.com/volcano-sh/volcano/pull/5349), @wangyang0616)
- **Cache-aware scheduler plugins**: Adds `Session.AddHintProvider` and QueueingHint-style event registration for unschedulable-job retries, plus structured `Status.InsufficientResources` and `PrePredicateError` rejection data. Rejections from plugins without safe hints fall back to normal scheduling. ([#5848](https://github.com/volcano-sh/volcano/pull/5848), @JesseStutler)
- **Nodegroup queue limits**: Adds the Queue annotation `volcano.sh/nodegroup-resource-limits`, containing a JSON mapping from nodegroup names to resource quantities. Limits are per queue and are not inherited by child queues. ([#5461](https://github.com/volcano-sh/volcano/pull/5461), @ruanwenjun, [Issue #4954](https://github.com/volcano-sh/volcano/issues/4954))

```yaml
metadata:
  annotations:
    volcano.sh/nodegroup-resource-limits: |
      {"fixed": {"cpu": "100", "memory": "200Gi"}, "overflow": {"cpu": "50"}}
```

- **Fairshare and usage arguments**: Adds the `fairshare.*` arguments and nested `usage` plugin `arguments.estimator` settings documented in the feature sections. The estimator keys are `request_ratio`, `burst_ratio`, `risk_threshold`, `risk_factor`, `be_cpu`, and `be_mem`. ### Security Fixes Included

#### [GHSA-j38h-7pfq-cxmw](https://github.com/volcano-sh/volcano/security/advisories/GHSA-j38h-7pfq-cxmw): DRA capacity accounting denial of scheduling service

Tenant-controlled device or minimum-task counts could trigger excessive iteration in DRA capacity aggregation. Calculations performed under the scheduler cache lock could exhaust CPU time and block scheduling for workloads across namespaces. The ResourceClaim-triggered path requires DRA support, explicit enablement of `DRAConsumableCapacity` (disabled by default), a capacity-bearing `ExactCount` request, and permission to create the associated ResourceClaim and Pod.

The fix replaces count-proportional loops with constant-time quantity multiplication, validates invalid counts, and uses overflow-safe device-count arithmetic. It was first released in v1.15.2 and is included in v1.16.0.

**Affected versions**: v1.15.0 and v1.15.1 (`>= 1.15.0, < 1.15.2`).

**Fixed versions**: v1.15.2 on the release-1.15 branch. Volcano v1.16.0 includes the fixes. Users on affected versions should upgrade.

**CVSS rating**: Medium, 6.5 (`CVSS:3.1/AV:N/AC:L/PR:L/UI:N/S:U/C:N/I:N/A:H`).

Reported and fixed by @thc1006, with advisory coordination by @JesseStutler. See [issue #5627](https://github.com/volcano-sh/volcano/issues/5627), the [capacity-scaling fix](https://github.com/volcano-sh/volcano/commit/c7fb3fe746cd80ef7a3c672218a9ae23b9e4a3c1), and the [v1.15.2 security release note](https://github.com/volcano-sh/volcano/releases/tag/v1.15.2).

## Upgrade Instructions

To upgrade after Volcano v1.16.0 has been published:

```bash
helm repo add volcano-sh https://volcano-sh.github.io/helm-charts
helm repo update
helm upgrade volcano volcano-sh/volcano \
  --namespace volcano-system --version 1.16.0

# Alternatively, for a manifest-based installation:
kubectl apply -f https://raw.githubusercontent.com/volcano-sh/volcano/v1.16.0/installer/volcano-development.yaml
```

- Update CRDs and RBAC together with the control-plane components, including NamespaceQueue and the new PodGroup/Numatopology fields. Follow the chart or installation method's CRD upgrade procedure and verify that the API server has the updated schemas before applying new fields.
- Review the Kubernetes compatibility matrix. Kubernetes 1.23 deployments are unsupported. Source builds require Go 1.26, and custom scheduler integrations must follow the updated Kubernetes APIs.
- Rebuild custom topology plugins for the new HyperNode gradient return types. Review custom scoring adapters against the upstream plugin-owned normalization path.
- NamespaceQueue and UnschedulableJobCache are disabled by default. Enable them explicitly after reviewing their scope. NamespaceQueue requires hierarchical capacity. This cache version does not cache hierarchical capacity rejections.
- Review custom scheduler configuration when enabling fairshare, load estimation, nodegroup limits, or topology anti-affinity. Fairshare must precede DRF for historical-usage ordering to take effect. Topology anti-affinity requires the new plugin and is not enforced for BestEffort Pods placed by backfill.
- When enabling new NUMA allocation reporting, update resource-exporter to a version supporting `spec.podAllocations`. Accelerator integrations likewise require compatible external device plugins and runtimes.
- When switching HyperNode ownership, roll out `disabled` mode before `standalone`. Embedded controller-manager mode remains the default.
- Helm admission-init Jobs now use TTL cleanup rather than immediate successful-hook deletion. The existing CRDs receive retention annotations so Helm uninstall preserves their resources. Inspect ownership and cleanup requirements when reinstalling. The new chart-managed NamespaceQueue CRD does not carry that retention annotation in this version.
- Gang-aware `gangPreempt` and `gangReclaim` remain explicit actions introduced in v1.15.0. This release does not merge them into the legacy `preempt` and `reclaim` actions.
