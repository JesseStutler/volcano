沿着一张 GPU，
看懂 DRA 的对象关系。

先看设备在哪里，再看需求如何找到它。三个典型场景，把 Node、ResourceSlice、DeviceClass 和 ResourceClaim 对到具体字段。

读图时，记住两条线。

供给侧：Node ← ResourceSlice → 设备

需求侧：Pod → Claim → Class

两侧通过「匹配」与「分配结果」连接。

NodeCLUSTER

设备可以从哪里访问？

本地设备通过 Slice 的 nodeName 对应节点。节点通常由 kubelet 注册。

ResourceSliceCLUSTER

有哪些设备、属性是什么？

DRA 驱动发布的库存清单；包含 pool、devices 和节点可访问性。

DeviceClassCLUSTER

什么样的设备符合要求？

管理员或驱动提供的选择规则与配置。用 CEL 匹配设备，集合可以重叠。

ResourceClaimNAMESPACE

想要什么、最终拿到了什么？

spec 描述请求，status 记录分配。Pod 引用同 namespace 的 Claim。

nodeName: node-a 说明设备在 node-a；devices 列出 gpu-0、gpu-1。设备分配后仍留在 Slice 中。

② 请求引用类别

③ 分配落到设备身份

status.allocation.devices.results 记录 driver、pool、device；本地设备的分配结果还限制可用节点。

三个名字别混淆

Pod 内别名 gpu → Claim 对象名 train-gpu → Claim 内请求名 accelerator。它们的连接可以在下方 YAML 中逐一找到。

同一张 A100，可以匹配两个 Class。

设备与 DeviceClass 是条件匹配关系，不存在独占归属。

↓ SVG↓ PNG↓ YAML
gpu-any：只选 driver

同时匹配两个 Slice 中的四张 GPU。DeviceClass 本身不会限定到某个节点。

gpu-a100：再选 model

增加 model == "A100" 后，只匹配 node-a。请求 gpu-a100 的 Pod 需要能访问该节点上的设备。

按 Class 计数有重叠

如果 node-a 的 gpu-0 被占用，按当前匹配关系统计，它在 gpu-any 和 gpu-a100 的 Used 中各出现一次；物理占用仍只有一张。

设备名不是全局 ID

两个节点都可以出现 gpu-0。这里 pool 分别为 node-a 和 node-b，所以它们是不同设备。

两个 Pod 引用同一个 Claim，仍是一份分配。

示意 trainer-a 已分配成功，trainer-b 随后复用 shared-gpu。

↓ SVG↓ PNG↓ YAML
共享的是 Claim 的分配结果

两个 Pod 都写 resourceClaimName: shared-gpu；不会因为多一个 Pod 就再分配 gpu-1。

本地设备约束两个使用者

gpu-0 只能从 node-a 访问，所以两个 Pod 都要满足该节点约束。status.reservedFor 记录允许使用 Claim 的消费者。

Used 按设备去重

第二个 Pod 复用已分配 Claim，新增设备需求为 0。共享访问不等于驱动自动提供时间片或显存隔离。

共享 Claim ≠ 多份 Claim

两个不同 Claim 默认不能同时独占同一设备。设备多份分配与 consumable capacity 是另外的机制，本页不展开。

教学对象 · 假想驱动 gpu.example.com · 三个场景独立阅读，不要混合批量应用
# 教学示例：Kubernetes resource.k8s.io/v1，假想驱动 gpu.example.com。
# Node 展示已有节点；ResourceSlice 通常由真实 DRA 驱动发布。
# 手工创建这些对象不会产生 GPU 或安装驱动。三个示例独立阅读。
apiVersion: v1
kind: Node
metadata:
  name: node-a
---
apiVersion: resource.k8s.io/v1
kind: ResourceSlice
metadata:
  name: node-a-gpus
spec:
  driver: gpu.example.com
  nodeName: node-a
  pool:
    name: node-a
    generation: 1
    resourceSliceCount: 1
  devices:
  - name: gpu-0
    attributes:
      model:
        string: A100
  - name: gpu-1
    attributes:
      model:
        string: A100
---
apiVersion: resource.k8s.io/v1
kind: DeviceClass
metadata:
  name: gpu-any
spec:
  selectors:
  - cel:
      expression: 'device.driver == "gpu.example.com"'
---
apiVersion: resource.k8s.io/v1
kind: ResourceClaim
metadata:
  name: train-gpu
  namespace: default
spec:
  devices:
    requests:
    - name: accelerator
      exactly:
        deviceClassName: gpu-any
        allocationMode: ExactCount
        count: 1
---
apiVersion: v1
kind: Pod
metadata:
  name: trainer
  namespace: default
spec:
  schedulerName: volcano
  restartPolicy: Never
  resourceClaims:
  - name: gpu
    resourceClaimName: train-gpu
  containers:
  - name: app
    image: busybox:1.36
    command: ["sh", "-c", "sleep 3600"]
    resources:
      claims:
      - name: gpu
        request: accelerator

YAML 使用 Kubernetes v1.36 的 resource.k8s.io/v1 结构。Node 通常由 kubelet 注册，ResourceSlice 通常由驱动生成；这些手写示例用于理解数据关系，手工创建对象不会产生 GPU。实际运行需要匹配的 DRA 驱动与 Volcano DRA 配置。

DEVICE IDENTITY

定位一张设备，要看三个字段。

(driver, pool, device)
(gpu.example.com, node-a, gpu-0)

设备是 ResourceSlice 里的条目，没有独立的 Device API 对象。Claim 的 allocation 通过这个三元组记录选择结果，不依赖 Slice 的名字。

Pool 也不是独立 API 对象。它是驱动划分的资源池；一个 pool 可以拆成多个 Slice。例子里 pool 恰好与节点同名，这只是命名选择。

resourceSliceCount 是同代 pool 的 Slice 数量，不是 GPU 数量；generation 标识 pool 的版本。读取方应忽略旧代，按分配要求处理不完整的 pool。

BACK TO BINPACK

统计的是设备集合，不是对象数量。

例 1 分配 gpu-0 后node-a / gpu-any
Allocatable · 匹配的库存设备2
Used · 已分配设备的交集1
新 Claim 请求一张卡新增 1
复用已分配的同一 Claim新增 0

库存和 Class 匹配关系可以缓存；分配状态要包含调度器尚未写回 API 的 Reserve，以及失败后的 Unreserve。

这是本地、独占设备的数量模型。不能用 Pod 数量估算 Used，也不能把重叠 Class 的库存直接加成物理总量。

补充边界：一个设备也可以被多个节点访问。

spec.nodeName 表示本地可访问性；allNodes: true 表示所有节点可访问；nodeSelector 可限制一组节点。这些是不同的发布方式。下面两个节点看到的是同一张卡，不是各有一张。

这也是 PR #6134 第一阶段只统计精确 NodeName 的原因：跨节点可访问的设备不能复制成各节点互相独立的库存。保存补充图 SVG
